# 分步创作流程与前后端职责

状态：待实现方案。本文对应用户提出的欢迎接入、任务选择、自由提示词、大纲确认、正文生成和导出流程。当前运行接口仍沿用交接说明中的既有实现，本方案不代表新接口已经可调用。

## 页面与任务分工

| 页面或步骤 | 后端负责人负责 | 前端队友负责 |
| --- | --- | --- |
| 欢迎首页 | 提供配置状态与进入工作区所需的服务可用信息 | 程序名、品牌故事的展示、视觉、路由与进入按钮 |
| API 与 ID 配置 | 接收配置、校验连接、管理服务端凭证并只返回配置状态；页面配置写入能力需新增 | 接入表单、掩码输入、验证按钮、成功失败提示 |
| 产品选择 | 产品目录、稳定 ID、版本与可用资料；校验用户选择 | 默认选项、搜索或下拉框、已选状态和返回修改 |
| 业务场景 | 定义场景 ID、标签、语义、默认值与校验规则，并明确人群和营销目标如何取值 | 显示默认选项、自定义输入和步骤导航 |
| 平台场景 | 维护平台枚举、结构、图片和长度规则，返回给后续 AI 流程使用 | 平台选择卡片、最多两个平台的限制及说明 |
| 自由提示词 | 把补充要求与产品证据、平台规则和系统提示词组合，处理缺失信息 | 提示词输入框、示例、长度提示、提交与重试 |
| AI 大纲 | 检索证据、生成结构化大纲、检查事实与引用，返回大纲 ID 和版本 | 大纲预览、标题与分段展示、加载及错误状态 |
| 修改大纲 | 保存手动修改、处理 AI 修改要求、更新版本并重新检查引用 | 编辑标题、增删与排序段落、编辑要点、输入修改要求、保存反馈 |
| 确认大纲 | 记录确认版本；正文接口检查该版本仍有效；修改后失效旧确认 | 确认按钮、未保存提示、确认状态、进入正文页面 |
| 正文生成 | 依据确认版大纲写作、配图、审稿，返回可追溯的结构化结果 | SSE 进度、平台预览、引用与配图、核验提示、停止及重试 |
| 导出 | 提供完整结果、来源与审核信息；未来增加服务端文件格式时负责生成与下载 | 当前 Markdown 与纯文本复制、下载按钮、选定标题和导出状态 |

品牌名称和故事文案由双方确认内容，前端负责呈现；它们不属于后端 AI 接口逻辑。API 凭证不进入前端代码、localStorage、日志或导出，后端不向浏览器回传已保存密钥的明文。

## 后端优先开发的能力

第一优先级是把当前一口气完成的策略、写作和审稿流程拆成大纲阶段与正文阶段，加入真正的用户确认边界。现有 server/pipeline.ts 会在完成策略后立即写正文，现有 /api/generate 与 /api/revise 没有大纲状态或确认版本参数。

建议先对齐以下五项能力，接口路径在实现前由双方另行确认，不把它们当作当前已经存在的路由。

| 待实现能力 | 输入核心字段 | 返回核心字段 |
| --- | --- | --- |
| 生成大纲 | 产品、业务场景、平台、自由提示词，以及明确的人群与目标 | outlineId、version、任务条件、各平台标题与段落、事实引用、配图计划、待确认项 |
| 保存大纲 | outlineId、预期版本、编辑后的标题与段落 | 新版本、保存后的完整大纲及校验问题 |
| AI 修改大纲 | outlineId、预期版本、修改要求 | 新版本、完整修改结果及变更提示 |
| 确认大纲 | outlineId、预期版本 | 已确认的 ID、版本与状态 |
| 按大纲生成正文 | outlineId、已确认版本 | SSE 进度和包含正文、图片、证据与核验的结果 |

欢迎页的运行时配置接入与业务选项读取也是新增能力。现在模型与 ima 凭证由后端环境配置读取，/api/status 提供状态，/api/connections/verify 验证现有 ima 配置；它们不能完成浏览器提交新密钥后的保存。

## 大纲确认规则

大纲使用结构化数据，每个平台分别保存标题、稳定的段落 ID、段落标题、要点、factIds 和配图计划。前端直接编辑这些字段，后端保存用户编辑后的版本，不用一整段不可解析的说明文字代替可编辑结构。

建议状态顺序为：任务录入 → 大纲生成中 → 大纲待确认 → 大纲已确认 → 正文生成中 → 正文完成。大纲待确认期间可反复手动修改或请求 AI 修改。

- 未确认大纲时，后端拒绝新流程的正文生成请求；前端同步禁用进入按钮。
- 修改产品、业务场景、平台、提示词或大纲内容时，受影响大纲需要重新校验并确认。
- 每次保存或 AI 修改产生新版本，旧版本的确认状态不自动继承。
- 确认和正文生成都校验 outlineId 与 version；过期版本冲突的状态码和响应在实现时纳入协议。
- 正文生成绑定确认时的大纲快照和证据；生成中再次编辑不改变已经启动的那次任务。
- 大纲确认不等于事实审核或发布通过，正文完成后仍展示独立核验结果。

## 产品业务平台与现有字段的对齐

产品选择沿用 productId，平台选择沿用 platforms。业务场景可映射到现有 scene，但现有接口还要求 audience；营销目标 goal 和购买阶段 buyingStage 也会影响策划。新页面没有单独询问这些信息时，后端需返回明确默认值、从已选场景给出可见建议，或追问补充，不隐藏猜测。

用户自由提示词可以作为现有 instructions 的输入来源，但系统提示词、产品知识检索与事实约束由后端维护。默认选项的 ID、标签、含义和默认值先由双方固定，前端显示文字与后端接收 ID 保持一致。

## 两人开始开发的顺序

1. 共同确认页面顺序、字段含义、大纲结构、修改方式及首版导出格式；首版可沿用当前 Markdown。
2. 后端先给出分阶段协议草案与新的大纲模拟数据，标明与现有 RunResult 样例的区别；前端开始页面导航和编辑器布局。
3. 后端依次完成大纲生成、保存与修改、版本确认、按确认版写作；前端逐一接入并覆盖失败与取消状态。
4. 联调验证一条完整流程，再验证未确认、未保存、修改后旧确认、过期版本和生成中修改等情况。

当前版本只新增职责与流程方案，没有新增上述路由、运行时设置接口、大纲类型或大纲 Mock。前端可先设计交互，正式实现前需以双方确认的新协议与新样例接入。

## 1 筛选结论与免费范围

优先选择本地可运行、具有明确开源许可、不依赖免费试用额度或额外付费图像生成 API 的方案。已有大模型服务、部署机器、存储和网络费用另计。软件开源不自动授权使用其演示图片、字体、品牌标识或第三方模板；实际纳入项目的素材需分别保留来源和许可。

| 渠道 | 首版方案 | 软件许可 | 最终交付 | 后续备选 |
| --- | --- | --- | --- | --- |
| 公众号 `wechat` | Wenyan Core | Apache-2.0 | 精排文章预览、可复制的微信富文本、封面 PNG | doocs/md；另行接入文颜 MCP 写草稿箱 |
| 小红书 `xiaohongshu` | xiaohongshu-card-skill 的多卡模板与本地渲染 | MIT | 3–6 张 PNG、正文、标签、整组下载 | xhs-card-renderer；复用自有 Playwright 图卡模板 |
| 门店朋友圈 `moments` | Satori 与 Sharp | MPL-2.0 与 Apache-2.0 | 1–3 张 PNG、独立短文案 | 经品牌改造的社交卡片模板 |
| 门店海报 `poster` | Satori 与 Sharp | MPL-2.0 与 Apache-2.0 | 1 张高清 PNG；需要时增加 PDF | 快图 MIT 开源前端，用于拖拽编辑 |

许可及原生能力见第 2 节对应来源。上述图片数量沿用项目现有平台规则，最终以当前代码和比赛要求共同校验；不把它们描述为平台官方的上传数量上限。

首版不引入 Polotno 商业 SDK、Placid 付费服务或依赖 Canva 付费套餐的能力。RedInk 的许可含非商业条件，不纳入本次面向营销应用的主选清单。

## 2 四个渠道的查询结果

### 2.1 公众号

**首选项目：文颜 Wenyan Core。**

- 仓库与许可：[caol64/wenyan-core](https://github.com/caol64/wenyan-core)、[Apache-2.0 LICENSE](https://github.com/caol64/wenyan-core/blob/main/LICENSE)。
- 原生能力：主题排版、微信公众号兼容处理、图片和脚注等发布前处理，提供 Web 与 Node.js 接入方式。
- 接口依据：[Node 环境渲染文档](https://github.com/caol64/wenyan-core/blob/main/docs/node.md)。文档提供 `@wenyan-md/core/node` 的 `renderStyledContent`，Node 方式使用 JSDOM，不能把它理解为已经自带截图或 PNG 导出。
- 视觉参考：[内置主题预览](https://yuzhi.tech/docs/wenyan/theme)。内置主题可作为排版起点，产品营销的封面、场景图片和品牌组件需要自行设计。

**建议接入方式。** 从服务器保存的 `Draft`、`Strategy` 和 `EvidenceBundle` 生成排版输入，再由文颜应用受控主题。Markdown 可以作为内部输入，最终界面展示实际排版文章，并提供微信富文本复制。浏览器复制需要写入 `text/html`，不能继续使用当前只写 Markdown 的 `navigator.clipboard.writeText` 作为公众号排版交付。

封面由自有模板渲染为 PNG。文章正文按现有规则编排 2–4 张同型号来源图，保留必要的图注和版本条件。手机预览建议采用约 390 CSS 像素的阅读宽度；这是本项目的预览默认值，不是微信接口约束。

**图片发布边界。** 本地 `/api/assets/:handle` 图片地址不能保证在公众号发布后仍可访问。未接公众号素材上传时，交付文章预览、排版复制和配图下载，并明确标识图片尚需上传，不能宣称已经发布就绪。启用公众号素材上传时，必须使用获授权的公众号账号，验证转存后的图片地址。

**可选能力。** [wenyan-mcp](https://github.com/caol64/wenyan-mcp) 支持主题和公众号草稿流程。写入草稿箱需要另行配置公众号 AppID、AppSecret、IP 白名单和相应账号权限，这些不是 ima 凭证。首版不依赖此能力，不自动对外发布。

**免费备选。** [doocs/md](https://github.com/doocs/md) 提供可私有部署的微信排版编辑器，仓库 [LICENSE](https://github.com/doocs/md/blob/main/LICENSE) 为 WTFPL。适合需要完整在线编辑器时评估；不能直接把其网页地址当成现成的渲染 REST API。

**本渠道验收。** 实际文章预览、富文本复制、封面文件均可用；标题、分段、图片、CTA 和事实限定词完整。以微信编辑器实际粘贴后的结果检查排版，并单独验证图片是否可访问。复制成功不等于图片已上传或文章已发布。

### 2.2 小红书

**首选项目：xiaohongshu-card-skill。**

- 仓库：[BboTTM/xiaohongshu-card-skill](https://github.com/BboTTM/xiaohongshu-card-skill)。
- 许可：[MIT LICENSE](https://github.com/BboTTM/xiaohongshu-card-skill/blob/main/LICENSE)。
- 文档列出的能力：封面、正文、总结页，以及默认 1080×1440 的多图卡片；仓库包含 HTML 模板、模式参考和 Playwright 渲染依赖。
- 安装依赖包含 npm 包与 Chromium。文档没有承诺一个可直接供本项目调用的统一 HTTP 接口，需要自行封装渲染工具。

**建议接入方式。** 先运行上游多图样例并核对输出，再选择性引入模板和渲染脚本。Agent 负责安排每页标题、正文、事实引用和来源图，后端把已审核内容写入受控模板并调用 Playwright，返回实际 PNG 文件。默认 1080×1440；高分辨率输出在联调中验证，不能只改 DPI 元数据后宣称像素变清晰。

固定首版页序为封面、具体场景、核心卖点、选购核对与 CTA，按内容需要合并为 3–6 页。设备主体来自 ima 的同型号原图。修改上游默认署名、头像和视觉风格，使之对应本项目和门店；保留源代码应有的版权及许可文件。

**事实边界。** 上游 Skill 的内容重写不能绕开本项目审核。建议只调用其排版和渲染部分，输入本项目已审核的稿件；如果为分页重新改写文案，需要回到事实及合规审核，不能直接输出。

**免费备选。** [cyrus-tt/xhs-card-renderer](https://github.com/cyrus-tt/xhs-card-renderer/blob/main/README.md) 为书页风格的轻量 Skill，使用 Playwright，把多页内容输出为 PNG，仓库有 [MIT LICENSE](https://github.com/cyrus-tt/xhs-card-renderer/blob/main/LICENSE)。其文档提供样例运行和命令行渲染方式，适合选购清单、知识卡片；产品大图与品牌风格仍需适配。

**本渠道验收。** 输出 3–6 张真实 PNG，序号正确、风格统一；封面与内页布局有区分；中文完整、文字不溢出、产品不变形。支持逐张下载和整组下载，并另外提供笔记正文与标签。出图本身不需要小红书登录，不把自动发布纳入本次任务。

### 2.3 门店朋友圈

**首选项目：Satori 与 Sharp。**

- [Satori 仓库与 MPL-2.0 许可](https://github.com/vercel/satori)。原生能力是把受支持的 JSX、样式和字体排版为 SVG，其 README 展示了结合 Sharp 转换为 PNG 的方式。
- [Sharp 仓库](https://github.com/lovell/sharp)、[Apache-2.0 LICENSE](https://github.com/lovell/sharp/blob/main/LICENSE)。用于图像格式转换和尺寸等处理。
- 这是可在后端调用的开源渲染能力，不自带完整的中文门店营销模板，也不要求部署到 Vercel。

**建议接入方式。** 在 Node.js 后端建立受控模板，Agent 只提供结构化文字、模板选择和本系统素材 ID。由 Satori 排版，Sharp 输出 PNG。字体文件作为项目依赖管理，显式载入具备使用许可的中文字库；不能假设宿主机一定有合适字体。图片由后端从已保存的证据包读取并传给渲染器。

首版建议固定三种模板：产品主图卡、场景拼图卡、单卖点到店卡。默认方形 1080×1080，可增加 1080×1440 竖图预设。每次输出 1–3 张图，短文案独立显示，便于销售员复制。

**设计要求。** 图中只突出一个核心卖点，保留产品完整名称和必要的适用条件；门店名称、地址、联系方式、活动二维码仅使用用户已经提供并确认的内容。没有输入时不编造，不擅自生成带业务承诺的默认信息。

**本渠道验收。** 同一稿件可重新选择模板并出图，文字内容保持一致；图片比例正确、边界有安全留白，下载后与预览一致。模板渲染不额外请求付费图像生成 API。

### 2.4 门店海报

**首版方案：复用 Satori 与 Sharp，后续增加快图编辑器。**

自动出图先复用朋友圈渲染底座，建立独立海报模板。默认输出 1080×1920 的电子海报，这是本项目的画布预设。主标题、副标题、产品主视觉、最多三个卖点和 CTA 分别布局；不得把小红书正文直接缩小塞进海报。

需要普通打印 PDF 时，可增加 [Playwright PDF 输出](https://playwright.dev/docs/api/class-page#page-pdf)，显式设置纸张尺寸、背景和边距。该功能需单独实现；Satori 与 Sharp 的首版 PNG 能力不等于已具备 PDF 导出。普通浏览器 PDF 也不等于已经满足印厂的 CMYK、出血或 PDF/X 要求。

**可编辑版本候选：快图 vue-fabric-editor。**

- 仓库：[ikuaitu/vue-fabric-editor](https://github.com/ikuaitu/vue-fabric-editor)，[MIT LICENSE](https://github.com/ikuaitu/vue-fabric-editor/blob/main/LICENSE)。
- 免费开源前端提供图层、字体、图片、二维码、模板、JSON 导入及 PNG、SVG、JSON 导出等能力。
- 该项目采用 Vue 和 Fabric.js；与当前 React 工作台对接时可采用独立编辑页面，再通过明确的消息协议传递经过校验的设计数据。
- 仓库把完整前后端和 HTTP 批量生成列为付费版能力。免费实现需要自行封装开源前端或渲染流程，不能直接依赖这些付费接口。
- 开源版效果入口：[在线演示](https://ikuaitu.github.io/vue-fabric-editor/)。

**本渠道验收。** 首版下载一张真实高清 PNG，最多三个卖点，长标题不会挤压产品图。若实现 PDF，单独验收实际页尺寸、图片清晰度和打印预览。快图后续版本再验收文字、图片、图层可编辑及 JSON 往返保存，不阻塞首版静态成品。

## 3 与现有项目的接入位置

现有工作台采用 React 19、TypeScript、Vite、Express 和 Node.js。文档整理时，`package.json` 尚未声明上述新渲染依赖。`RunResult` 包含 `Draft`、`EvidenceBundle`、`ReviewReport` 等结构，但没有视觉成品列表。前端 `exportContent` 仍生成 Markdown 文件，`copyContent` 仍复制纯文本内容。

实现前阅读项目 [AGENTS.md](../../../../AGENTS.md) 和 [接口交接固定入口](../../README.md)，重新核对当前代码，避免把资料整理时的代码状态当成永远不变的接口。

| 现有模块 | 实现 Agent 应复用的能力 | 新增内容 |
| --- | --- | --- |
| `shared/types.ts` | `Platform`、`Draft`、`ImagePlacement`、`EvidenceBundle`、`RunResult` | 成品与渲染结果类型，明确为新增协议 |
| `server/index.ts` | 已保存任务、任务版本、现有请求及图片句柄 | 渲染和成品访问路由，复用同一服务 |
| `server/pipeline.ts` | 已审核稿件和事实来源 | 在正文审核完成后衔接渲染，不在排版阶段新增产品事实 |
| `server/knowledge.ts` | 证据素材与图片读取 | 通过后端素材解析取得实际图片，不向第三方外发签名链接 |
| `src/App.tsx` | 当前平台、选定标题、审核面板与修改入口 | 成品预览、模板选择、重新渲染和文件下载 |

建议新增 `server/render/` 组织适配器及模板。路径是实施建议，当前没有创建这些业务模块。不要为首版增加一个必须单独登录的设计平台。

**Skill 与运行时的区别。** 把 Skill 安装进 Codex 或其他开发客户端，只影响开发客户端的工作方式，不会自动让网页后端获得出图能力。我们的 Express Agent 必须实际调用 Node 库、渲染脚本或自己封装的工具函数，再把二进制成品交给浏览器。

既有分步流程文档包含大纲确认等待实现方案。本次渲染能力接在最终正文及审核之后，不把“大纲生成”与“视觉成品生成”混为同一个步骤。既有文档中“首版可沿用 Markdown”的导出规划，以本次用户要求的视觉成品优先；Markdown 可以保留为说明附件。

## 4 建议的工具与接口草案

本节是供实现 Agent 对齐的新增方案，不属于当前可调用接口。保持现有 `/api/generate`、`/api/revise` 和 SSE 事件兼容，首版用独立渲染请求取得成品，无需先改写原有生成协议。

建议封装 `renderWechatArticle`、`renderXhsCards`、`renderMomentsCards` 和 `renderStorePoster` 四个工具，共用素材解析、模板配置、成品保存与来源映射。

建议新增 `POST /api/render`，由服务端根据 `runId` 查找已有任务和证据。请求只允许选择任务、平台、已有标题及受控模板；不接受客户端提交任意脚本、文件路径、产品事实或外部图片 URL。

```ts
// 新增协议草案，尚未写入 shared/types.ts。
interface RenderRequest {
  runId: string;
  revision: number;
  platform: Platform;
  selectedTitleIndex: number; // 从 0 开始
  templateId: string;
}

interface RenderArtifact {
  id: string; // 本系统成品句柄
  role: 'article' | 'cover' | 'card' | 'poster';
  format: 'wechat-richtext' | 'png' | 'svg' | 'pdf';
  previewUrl: string;
  downloadUrl?: string;
  width?: number; // 栅格图的实际像素
  height?: number;
  sourceImageIds: string[]; // 本系统 ImageAsset.id，不是 ima media_id
  factIds: string[];
}

interface RenderBundle {
  runId: string;
  revision: number;
  platform: Platform;
  templateId: string;
  artifacts: RenderArtifact[];
  reviewStatus: ReviewReport['status'];
  warnings: string[];
}
```

建议新增 `GET /api/render-assets/:handle` 返回允许访问的成品。公众号富文本读取方式在实现协议中明确，预览地址和下载地址可以共用服务器句柄，但下载需给出正确的 MIME 和文件名。不要返回服务端绝对路径。

首版按单个平台同步完成渲染再返回结果；渲染器限制同时工作的任务数，并允许取消。任务不存在或过期沿用 410 语义，版本或可导出状态冲突建议使用 409，非法模板或标题索引使用 400。超时及第三方渲染失败使用明确的失败响应，不能返回 HTML 错误页面冒充 PNG。具体新增响应需随实现进入类型、请求样例和新交接版本。

成品可以保存在已被 Git 忽略的 `.cache/render/`，访问生命周期与任务的 30 分钟失效策略对齐。正文修订产生新任务后必须重新渲染；旧成品保持旧版本标识，不能继续显示为当前版本。

## 5 实现边界与素材处理

1. 渲染以服务端已经保存的稿件和证据为依据。产品型号、参数、价格、系统与限定条件不能由模板补齐，也不能因自动分页或缩放被删掉。
2. 正式模式的产品图从 ima 证据包取得，保存原图与成品的映射。设备主体保持原貌，标题、背景色和装饰通过排版合成；生成式重绘设备不属于本次方案。
3. 图片不足时显示缺口，不通过复制同一图片来掩盖原始素材数量不足。装饰形状和信息卡不计作额外的 ima 产品素材。
4. 渲染器使用受控模板。模型只生成数据与版式意图，不直接提供可执行 JavaScript。调用脚本使用参数数组，不能拼接模型输出作为 shell 命令。
5. 中文字体随实现登记来源和许可。截图等待字体和图片加载完成。使用实际渲染高度检测溢出；文字放不下时调整排版或请求精简，不截断事实限定条件。
6. 保留原有审核状态。`blocked` 只允许明确标记的预览，不提供正式发布成品；`needs_attention` 保留待确认标记；`passed` 表示相应内容检查通过，不表示已完成账号发布或印刷验收。
7. 审核报告与广告版面分开展示。导出包附可读来源说明、审核状态和必要的待确认项，不包含原始知识库全文、ima 内部 ID、密钥、临时签名 URL 或请求头。
8. 小红书、朋友圈和公众号的自动发布，以及公众号账号配置写入，均不属于本次首版必需能力。生成、下载、写入草稿箱、公开发布是不同动作，界面须准确标识实际完成状态。

## 6 执行顺序与交付要求

### 第一阶段 证明工具能产生真实文件

1. 固定上游仓库提交或 npm 版本，保留许可文件。先检查上游样例、依赖和脚本入口；不要在文档未核对的命令上假设可直接运行。
2. 在隔离目录用纯模拟文案和测试图分别完成一份文颜排版、一组小红书 PNG、一张 Satori 朋友圈图和一张 Satori 海报。
3. 逐张打开输出文件，记录尺寸、字体、图片载入和实际效果。小红书首选若不能完成渲染或满足品牌图布局，采用该渠道的免费备选或自有 Playwright 模板，记录切换原因。

### 第二阶段 接入现有 Agent

1. 建立统一工具输入与结果类型，保持四个 `Platform` ID 不变，接入已审核稿件和真实证据素材。
2. 实现安全的模板填充、素材解析、成品保存和访问，新增渲染请求及错误状态。
3. 前端增加“生成成品”“换模板”“下载图片”“整组下载”等操作；公众号增加排版复制并准确提示图片转存状态。
4. 修改正文后使旧成品失去当前版本标识；换配色和版式可仅重新渲染，改写产品文案必须重新审核。

### 第三阶段 交接可检查的实例

实现 Agent 应交付四渠道各至少一组实际成品和预览截图，以及启动方式、依赖版本、模板位置、许可清单、失败示例和测试结果。四个渠道的风格应对应各自使用方式，不只改变画布尺寸。

如实现新增 HTTP 路由或共享类型，按 [项目协作规则](../../../../AGENTS.md) 新增完整接口归档，包含最新类型、输入校验、请求样例、模拟响应、前端适配说明和实际验证记录。现有历史版本不覆盖。

## 7 验收清单

| 类别 | 必测情景 | 通过标准 |
| --- | --- | --- |
| 公众号 | 中文长文、标题、2–4 张来源图、复制排版 | 实际预览完整，微信粘贴样式经检查；图片转存状态准确 |
| 小红书 | 3–6 页、长标题、产品图与限定词 | 每页 PNG 可打开、顺序正确、字体无缺字、无文字溢出 |
| 朋友圈 | 单图与多图、方形与竖形模板 | 图文重点清晰，短文案可单独复制，预览与下载一致 |
| 海报 | 最多三个卖点、产品主视觉、长 CTA | 产品比例正常，标题和 CTA 完整，PNG 尺寸正确 |
| 可选 PDF | 指定纸张和页边距 | 实际页面尺寸正确，字体和图片正常，不冒充印厂认证 |
| 来源 | 近似型号、缺图、过期素材 | 不串型号；缺图和过期有错误或警示；可追溯到本次证据 |
| 审核 | blocked、needs_attention、本地演示 | 不消除原有状态，不将模拟结果标记为正式 ima 结果 |
| 修改 | 生成成品后修改正文或切换标题 | 渲染结果绑定正确任务与版本，不复用错误旧稿 |
| 导出 | 单图、整组、富文本、失败下载 | 返回实际文件及正确 MIME；不以代码或占位图代替成品 |
| 隐私 | 访问句柄和下载来源说明 | 不暴露凭证、真实知识库 ID、绝对文件路径和签名链接 |
| 免费边界 | 清洁环境完成四渠道渲染 | 不要求新增商业 SDK 许可证或付费图像生成 API |

外部工具可运行、项目接口联调成功、营销内容审核通过、渠道发布成功，应分别记录。不得把其中某一项成功替代其余验收。

## 8 实现 Agent 的开始任务

> 阅读项目 AGENTS.md、docs/api/README.md 和本文。保留现有模型调用、ima 检索、事实审核和前后端协议。先用免费开源工具完成四渠道真实成品：公众号接文颜 Core，小红书接卡片 Skill 的模板与 Playwright，朋友圈和海报接 Satori 与 Sharp。先跑工具样例，再封装后端渲染能力与前端成品预览下载。产品图使用本次证据包的同型号原图，字体、模板和依赖记录许可。最终提供四渠道可打开的成品文件及实际截图，并按仓库规则新增接口归档。不要仅返回 HTML 或 Markdown 源码，也不要把安装开发客户端 Skill 当成网页 Agent 已获得渲染能力。

当前运行接口与本次研究方案分别管理。实施时以固定入口的最新协议为准；本次查询结果不承诺上游项目已经在当前机器安装，也不授权自动公开发布内容。
